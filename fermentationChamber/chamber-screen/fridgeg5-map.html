GPIO and peripherals

Every gpio_set_level (0x40153464), gpio_get_level (0x4015354c) and ADC call site in the image was enumerated and its argument resolved. 26 output sites, 25 input sites, 0 with a non-constant argument — so this is the complete pin inventory, not a sample. An exhaustive scan of every gpio_set_level, gpio_get_level and gpio_set_direction call site — including indirect calls through a function pointer — finds no reference to either pin. No DAC, LEDC, MCPWM, touch, ADC2, RMT, I2S or PCNT code is linked into the stock image either.

That indirect-call caveat matters: an earlier scan of this image looked complete and was not. The DC line on GPIO 2 is set through a callx8 in an IRAM callback, so it never appeared in an enumeration of direct call8 sites. Any claim that a pin is unused is only as good as the scan behind it.

Temperature probe

Despite the recovery screen showing two columns, only one ADC channel is read anywhere in the firmware — recovery mode and main application alike. There is one wired probe, not two.

ADC1 ch 6 = GPIO 3412-bit 11 dB attenVref 1100 mV

The main application samples 128 times in a tight loop, accumulates, and takes sum >> 7 as the mean. Each raw sample is range-checked and the reading is invalidated if any falls outside roughly 2–4093 — that is open-circuit and short-circuit probe detection. The mean goes through esp_adc_cal_raw_to_voltage.

The divider maths, read instruction-for-instruction from the stock routine at 0x40107e65:

R = 56000 × V / (3300 − V) 56 kΩ seriesthermistor on the low side

The curve is a beta equation with runtime parameters, fetched by nonvolatile_get_float() as NVS keys ntc_beta0 / ntc_t0 / ntc_r0 (float key indices 5, 6, 7), falling back to a defaults table at 0x3f40e0c4:

ntc_beta0 = 3950ntc_t0 = 298.15 K ntc_r0 = 100 kΩ

So a 100 kΩ NTC, β=3950, referenced at 25 °C, with 1/T = 1/ntc_t0 + (1/ntc_beta0) ln(R/ntc_r0). A second identical set (ntc_beta1/t1/r1) serves the second probe channel. Per-unit correction comes from cal_temp0/cal_adc0, cal_temp1/cal_adc1 and temp_offset, which a factory-commissioned unit carries in NVS.

An earlier revision of this page said 10 kΩ. That constant does sit in the same literal pool but belongs to unrelated code — the series resistor is 56 kΩ.

Display

An ST7789V panel driven through a modified lvgl_ili9341 component. The presence of spi_display_probe.c means the panel is auto-detected, so more than one variant exists across the product line — do not hard-code the controller in replacement firmware without probing.

All six recovered exactly. MOSI, SCLK and CS come from the spi_bus_config_t and spi_device_interface_config_t structs built at 0x401844a4. RST is GPIO 4 — probe_spi_init pulses it high/20 ms/low/20 ms/high. Backlight is GPIO 27, beside the "%s backlight." strings.

DC is GPIO 2, and it hides from a naive scan: the SPI pre-transfer callback at 0x40090660 does movi.n a10, 2 ; callx8 → gpio_set_level. Because that is an indirect callx8 rather than a direct call8, it does not appear in an enumeration of gpio_set_level call sites. GPIO 2 is a boot strapping pin, so it must not be held high at reset.

Confirmed on hardware: the panel takes RGB565 most-significant byte first. Filling with 0x001F (blue) unswapped renders as 0x1F00 — green.

On-device tooling

Recovery mode

A complete diagnostic menu already built into the firmware, driven by the device’s own buttons and screen rather than a serial console — “Press up/down to change option, select to perform action”. It exercises every output, reads every input, and samples both ADC channels, which makes it the fastest route to confirming a pin map on real hardware.

Cloud protocol

How the device reaches KegLand

HTTPS only bootstraps the session; the working channel is Azure IoT Hub over MQTT. In every endpoint below, %s is a runtime-substituted domain — test.rapt.io also appears in the image as a staging host.

Device-code pairing

Requests a user code, then polls for the token. This is the “enter this code on the portal” flow — no password is ever stored on the device. Recovered at 0x400fb7b0.

POST https://id.%s/connect/deviceauthorization — client_id=rapt-device
POST https://id.%s/connect/token — grant_type=device_code | refresh_token

Hub handoff

Posts the MAC address and receives a connectionString back. This is the pivot point from HTTPS to MQTT. Recovered at 0x400fc080.

POST https://api.%s/api/device/fridge/connect — macAddress=%s → connectionString

Profiles

Fermentation profiles and their step lists are fetched over HTTPS, not pushed over MQTT. Recovered at 0x400fc230.

GET https://api.%s/api/device/fridge/GetProfileIds
GET https://api.%s/api/device/fridge/getProfile — macAddress=%s&profileId=%s

Telemetry and twin

Steady-state operation. Measurements go up as telemetry; configuration comes down as Azure device-twin desired properties, listed below.

Two things worth noting

There is a genuine PID controller in the firmware — pidP, pidI, pidD and SetPIDEnabled — not merely bang-bang control with hysteresis, and its gains are twin-configurable. Separately, gravity participates in the alert path: currentGravity and currentGravityVelocity are sent to notify, so the Pill’s readings drive decisions rather than only being logged.

TLS trust store

A fixed root_ca[] bundle of 6516 bytes, installed via esp_tls_set_global_ca_store() from both app_main and wifi_init_sta. Four public roots, no more — this is not the full ESP-IDF certificate bundle.

ISRG Root X1DigiCert Global Root G2 Microsoft RSA Root CA 2017Baltimore CyberTrust — expired 2025-05-12

Build a current bundle for replacement firmware rather than copying this one. A hardcoded trust store is also a plausible cause if stock units begin failing to connect.

No embedded credentials

There is no private key material and no device certificate anywhere in the 4 MB image. The PEM markers near 0x3f45893e are mbedTLS parser format constants, not key data.

Device identity is established entirely at runtime — the OAuth device flow yields a refresh token, and fridge/connect yields the Azure connection string. Both live in nvs, not in the app image. Replacement firmware has nothing to extract and must simply re-pair.

Before flashing anything

The full 4 MB dump includes nvs, which holds the device registration and refresh token — keep it, because restoring it is what saves you from re-pairing. Note also that the stock firmware checks for and applies OTA updates on its own, so custom firmware left reachable by that path could be overwritten by the vendor. A 64-character high-entropy string appears twice in the image; it was investigated and is benign — part of the self-signature of a public root certificate in the bundle above.

Correction: this page previously suggested KegLandisAwesome! was the provisioning AP password. It is not. The captive-portal password is generated per unit and stored in NVS under appwd in the espwifimgr namespace, so it differs on every device.
